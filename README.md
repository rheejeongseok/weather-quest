# 웨더 퀘스트

날씨와 실제 착용 피드백을 바탕으로 나에게 맞는 옷차림을 찾아가는 모바일 중심 반응형 웹입니다. 모바일·태블릿·PC에서 같은 닉네임으로 설정과 기록을 이어서 사용할 수 있습니다.

- 서비스: https://weather-quest-jet.vercel.app
- GitHub: https://github.com/rheejeongseok/weather-quest
- 배포: Vercel의 정적 화면 + Node.js 서버 함수
- 저장: 배포 환경은 Supabase, 환경변수가 없는 로컬은 SQLite
- 실행 환경: Node.js 24.x, 추가 패키지 설치 불필요

## 화면과 주요 기능

| 탭 | 기능 |
| --- | --- |
| 날씨 | 현재 기온, 하루 최저·최고, 오늘·내일 아침 비교, 3시간 간격 예보, 목표 보온량과 계산 내역 |
| 옷 조합 | 종류별 옷 선택, 소재·두께 변경, 보온 합계와 목표 비교, 선택 비우기·추천으로 초기화 |
| 착용 기록 | 실제 입은 조합과 시간·장소·5단계 착용감 저장 |
| 기록 관리 | 날짜별 기록 조회, 수정·삭제, 페이지 이동 |
| 설정 | 생활 패턴·체감 체크·추천 취향, JSON 백업·가져오기 |

모바일에서는 하단 메뉴로 화면을 전환합니다. 날씨 표와 옷 종류 메뉴는 내부 가로 스크롤을 지원합니다. 파비콘은 SVG·ICO, 아이폰 홈 화면용 아이콘은 PNG로 제공합니다.

### 날씨

서울·부산·인천·대구·대전·광주·제주를 지원합니다. Open-Meteo에서 현재 날씨와 시간별 예보를 받아 서버에서 10분 동안 캐시합니다. 3시간 간격 표에는 기온·체감온도·강수확률·바람을 표시합니다.

옷차림 추천과 오늘·내일 아침 비교는 설정한 외출 시각을 기준으로 합니다. 착용 기록의 날씨는 선택한 시각의 예보이며 관측 실황이 아닙니다. 날씨 연결 실패 시 임의의 데이터를 대신 표시하지 않습니다.

### 개인 설정과 추천 스타일

- **생활 패턴:** 지역, 외출 시각, 활동량, 야외 체류 시간, 이동수단
- **체감 체크:** 추위·더위 민감도, 바람 민감도, 땀 성향
- **추천 취향:** 간단하게 / 균형 있게 / 여러 겹으로

추위와 더위 민감도는 기온에 따라 따로 반영합니다. 바람 민감도는 방풍 겉옷의 우선순위에 사용하며, 땀 성향과 이동수단은 옷을 조절하는 안내에 활용합니다. 스타일은 필요한 보온량 자체가 아니라 조합의 겹 수와 순위를 바꿉니다.

### 옷 조합

상의는 최대 5벌까지 기록할 수 있습니다. 반팔 + 셔츠 + 바람막이처럼 같은 분류의 옷도 겹쳐 입을 수 있습니다. 이너·티셔츠·셔츠·맨투맨·니트·가디건·후드집업·플리스·재킷·코트·패딩 등을 지원하며 얇음·기모·안감·충전 부피를 구분합니다.

오늘과 내일의 조합은 별도로 유지합니다. **선택 비우기**는 모든 선택을 해제하고, **추천으로 초기화**는 현재 날씨·개인 설정에 맞는 추천 조합을 복원합니다. 조합을 실제 착용 기록에 적용한 뒤 피드백을 저장합니다.

### 날짜별 기록과 동기화

닉네임은 앞뒤 공백·유니코드 표기·영문 대소문자를 정규화합니다. 닉네임 방식은 인증이 아니며, 닉네임을 아는 사람은 같은 프로필을 조회·수정할 수 있습니다.

사용자별 하루 한 기록을 유지합니다. 서버는 저장 ID를 `day:YYYY-MM-DD`로 정규화하여 같은 날짜 재저장을 수정으로 처리합니다. 과거 기록을 수정할 때는 당시 날씨와 시각을 유지합니다.

삭제한 기록은 목록과 개인화 계산에서 제외합니다. 구형 중복이나 백업으로 되살아나지 않도록 날짜별 최소 삭제 표시를 남기며, 사용자가 같은 날짜를 명시적으로 다시 기록하는 것은 가능합니다.

배포 DB를 사용하는 기기는 재접속·새로고침 시 최신 기록을 가져옵니다. 다른 기기에서 수정한 화면을 실시간으로 자동 갱신하는 기능은 아직 없습니다. 브라우저에는 마지막 닉네임만 기억합니다.

## 목표 보온량의 기준

```text
기온 기준 = 1 + (26 - 체감온도) × 0.3  [1~12점]
최종 목표 = 기온 기준 + 개인 보정 + 활동량 + 야외 시간  [1~12점]
```

개인 보정·활동량·야외 시간 보정이 0이면 다음과 같습니다.

| 체감온도 | 기본 목표 |
| --- | --- |
| 20℃ | 2.8점 |
| 10℃ | 5.8점 |
| 0℃ | 8.8점 |

비슷한 체감온도의 실외 착용 피드백에 더 높은 비중을 주고, 초기 민감도 설정을 사전값으로 사용합니다. 당시 활동량과 야외 시간을 개인 민감도 학습에서 분리하며 실내 피드백은 제외합니다. 활동량은 -1~+1점, 추운 조건의 야외 시간은 최대 -0.4~+0.4점으로 보정합니다.

**기본식과 보정 폭은 검증 중인 앱 가정입니다.** 보온 점수는 상의 조합의 상대적인 비교 지수이며 특정 제품의 실측 보온 성능이나 전신 단열량이 아닙니다. 외부 의복 단열 자료를 검토했지만 한국 사용자의 기온·실제 착장·체감을 현재 점수로 직접 환산할 데이터는 확보하지 못했으며, 통계로 학습된 추천이라고 주장하지 않습니다.

날씨 화면의 **목표 점수 계산 기준 보기**에서 적용된 기온·각 보정값·비슷한 기온의 기록 수를 확인할 수 있습니다.

- [개인화 계산과 검증](docs/PERSONALIZATION.md)
- [소재·두께별 보온 분류](docs/WARMTH.md)
- [외부 자료와 기본 점수 재점검](docs/BASELINE-REVIEW.md)

## 로컬 실행

```powershell
git clone https://github.com/rheejeongseok/weather-quest.git
cd weather-quest
npm start
```

기본 주소는 http://localhost:3002 입니다. 같은 Wi-Fi의 다른 기기는 `http://PC의내부IP:3002`로 접속합니다. 서버가 실행 중이어야 하며 Windows 방화벽에서 해당 포트 접근이 허용되어야 합니다.

Supabase 환경변수가 없으면 `data/weather.sqlite`를 생성합니다. 로컬 SQLite 데이터는 배포 서버와 공유하지 않습니다. `PORT`, `HOST`, `DATA_DIR`로 포트·바인딩 주소·로컬 DB 폴더를 바꿀 수 있습니다.

### 로컬에서도 Supabase 사용하기

`.env.example`을 `.env.local`로 복사한 뒤 같은 프로젝트의 URL과 서버용 키를 넣습니다.

```dotenv
SUPABASE_URL=https://jzzdgoirtokaiwwmmitd.supabase.co
SUPABASE_SECRET_KEY=서버용_Secret_key
```

```powershell
node --env-file=.env.local server.mjs
```

`npm start`는 `.env.local`을 자동으로 읽지 않습니다. 키가 들어간 파일은 Git에서 제외되며 비밀 키를 소스나 브라우저 코드에 넣지 않습니다.

## Supabase · Vercel 배포

현재 사용자가 지정한 서울 프로젝트의 연결 주소는 `https://jzzdgoirtokaiwwmmitd.supabase.co`입니다. 이전 싱가포르 프로젝트의 URL과 키를 혼용하지 않습니다. 아래 설정은 사용자가 대시보드에서 적용해야 하며 저장소의 예제 파일만 바꿔서는 실제 배포 환경변수가 변경되지 않습니다.

1. 서울 프로젝트 SQL Editor에서 [schema.sql](supabase/schema.sql)을 실행합니다.
2. Vercel 환경변수에 `SUPABASE_URL`과 **같은 서울 프로젝트의** `SUPABASE_SECRET_KEY`를 등록합니다. 사용하는 Production·Preview 환경에 적용합니다.
3. GitHub 저장소를 연결하고 Framework Preset은 **Other**, Node.js는 **24.x**, Root Directory는 저장소 루트로 설정합니다.
4. 빌드·출력 설정은 `vercel.json`을 사용합니다. 빌드는 `npm run build`, 출력 폴더는 `dist`이며 API는 `api/handler.mjs`가 처리합니다.
5. 환경변수 변경 후 재배포합니다. 기존 배포에는 변경값이 소급 적용되지 않습니다.

Vercel에서는 Supabase 설정이 빠지면 오류를 반환하며 임시 SQLite로 대체하지 않습니다. 현재 DB 스키마는 `wq_profiles`, `wq_records`, 병합 함수 `wq_import_records`를 사용합니다.

- [단계별 배포 안내](docs/DEPLOY.md)
- [싱가포르에서 서울로 이전하기](docs/SEOUL-MIGRATION.md)

### 연결 오류 확인

| 오류 | 확인할 항목 |
| --- | --- |
| 환경변수 누락 | 두 변수의 이름·값·적용 환경, 재배포 여부 |
| DNS 조회 실패·서버 연결 실패 | 새 Project URL인지, 오타·이전 주소·프로젝트 실행 상태 |
| 키 인증 실패 401 | URL과 키가 같은 프로젝트인지, 키 활성 상태 |
| 접근 권한 오류 403 | 서버용 키 종류와 테이블 권한 |
| 테이블·함수 없음 404 | 새 프로젝트에서 `schema.sql` 실행 여부 |

`SUPABASE_URL`에는 대시보드 주소 대신 `https://프로젝트ID.supabase.co` 형태의 Project URL을 넣습니다. 비밀 키는 앞뒤 여백을 정리하며 내부 공백·줄바꿈은 오류로 안내합니다.

## 백업과 프로젝트 이전

설정의 JSON 내보내기는 현재 닉네임의 프로필 정보와 기록을 저장합니다. 가져오기는 **현재 프로필에 없는 날짜의 기록만** 추가하며 기존 날짜·설정은 덮어쓰지 않습니다. 적용 전 현재 데이터를 백업 다운로드합니다.

전체 Supabase 이전은 JSON 가져오기와 별개입니다. [export-migration.sql](supabase/export-migration.sql)은 모든 프로필·설정·기록·삭제 표시를 이전할 SQL을 생성하는 읽기 전용 도구입니다. 실제 이전 절차와 확인 사항은 [서울 이전 안내](docs/SEOUL-MIGRATION.md)를 따릅니다. 현재 앱의 두 테이블을 대상으로 하며, 대규모 DB에는 공식 dump/restore 절차를 사용합니다.

## 검증

```powershell
npm test
npm run build
```

추천 계산·개인 설정·겹쳐 입기·DB 영속성·날짜별 수정·삭제·백업 병합·연결 오류 처리를 검증합니다. 자동 테스트 통과는 실제 추천 정확도의 실증 검증과 구분합니다.

Windows에 Chrome이 설치되어 있으면 실제 브라우저 검증도 실행할 수 있습니다.

```powershell
node scripts/browser-check.mjs
```

390·768·1440px에서 화면 넘침, 탭, 상세 설정, 초기화, 조합·피드백 저장, 수정·삭제를 확인합니다. 별도 임시 DB를 사용하고 캡처는 Git에서 제외된 `.qa/`에 저장합니다. `--icons` 옵션은 SVG에서 ICO와 아이폰용 PNG를 다시 렌더링합니다.
