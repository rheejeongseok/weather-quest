## Cloth to You

> 이전 이름: 웨더 퀘스트(Weather Quest), Cloth to You. 아래 서비스·GitHub 주소는 저장소와 Vercel 프로젝트 이름을 바꾸기 전까지 기존 주소를 사용합니다. DB 테이블(`wq_*`)과 브라우저 저장 키(`wq-nickname`)는 기존 데이터를 유지하기 위해 그대로 둡니다.

날씨와 실제 착용 피드백을 바탕으로 나에게 맞는 옷차림을 찾아가는 모바일 중심 반응형 웹입니다. 모바일·태블릿·PC에서 같은 닉네임으로 설정과 기록을 이어서 사용할 수 있습니다.

- 서비스: https://weather-quest-jet.vercel.app
- GitHub: https://github.com/rheejeongseok/weather-quest
- 배포: Vercel의 정적 화면 + Node.js 서버 함수
- 저장: 배포 환경은 Supabase, 환경변수가 없는 로컬은 SQLite
- 실행 환경: Node.js 24.x, 추가 패키지 설치 불필요

### 날씨

서울·부산·인천·대구·대전·광주·제주를 지원합니다. Open-Meteo에서 현재 날씨와 시간별 예보를 받아 서버에서 10분 동안 캐시합니다. 3시간 간격 표에는 기온·체감온도·강수확률·강수량(그 시각부터 3시간 합계)·바람을 표시합니다. 현재 강수량과 하루 강수량 합계도 함께 보여 주며, 착용 기록에도 그 시각의 강수량 예보를 저장합니다.

옷차림 추천과 오늘·내일 아침 비교는 설정한 외출 시각을 기준으로 합니다. 착용 기록에는 외출 시간대의 예보를 저장하고, 지난 날짜의 기록은 다음 접속 때 Open-Meteo 과거 시간별 값(관측을 반영한 모델 값, 관측소 실측 아님)으로 보정해 범위 학습에 우선 사용합니다. 날씨 연결 실패 시 임의의 데이터를 대신 표시하지 않습니다.

### 개인 설정과 추천 스타일

- **생활 패턴:** 지역, 외출 시각, 활동량, 야외 체류 시간, 이동수단
- **체감 체크:** 추위·더위 민감도(각 5단계, 덜 타는 쪽 포함), 바람 민감도(5단계), 먼저 시린 부위, 땀 성향(4단계), 일교차 민감도
- **추천 취향:** 겹 수(적게/보통/여러 겹), 이너 선호, 주로 입는 겉옷, 즐겨 입는 상의, 추천에서 뺄 옷

추위와 더위 민감도는 기온에 따라 따로 반영합니다. 기존 0~2 저장값은 같은 의미로 유지되고, 덜 타는 쪽(-1·-2)이 추가됐습니다. 바람 민감도는 방풍 겉옷의 우선순위에 사용하며, 시린 부위·땀 성향·일교차·이동수단은 옷을 조절하는 안내에 활용합니다(몸통이 먼저 추운 경우만 같은 범위에서 이너 조합을 조금 우선). 추천 취향은 필요한 보온량 자체가 아니라 같은 범위 안의 조합 순위를 바꿉니다. 추천에서 뺄 옷은 자동 추천에서만 제외하며, 제외하면 맞는 조합이 없을 때는 제외 없이 추천합니다.

### 옷 조합

상의는 최대 5벌까지 기록할 수 있습니다. 반팔 + 셔츠 + 바람막이처럼 같은 분류의 옷도 겹쳐 입을 수 있습니다. 이너·티셔츠·셔츠·맨투맨·니트(터틀넥 포함)·가디건·후드집업·플리스·조끼·바람막이·재킷·블레이저·가죽 재킷/무스탕·야상·코트·패딩·롱패딩 20종을 지원하며 얇음·기모·안감·충전 부피를 구분합니다.

옷 목록은 자주 입은 옷을 위로 올리고, 설정에서 추천에서 뺀 옷은 접어 둡니다(선택한 옷은 항상 표시). 오늘과 내일의 조합은 별도로 유지합니다. **선택 비우기**는 모든 선택을 해제하고, **추천으로 초기화**는 현재 날씨·개인 설정에 맞는 추천 조합을 복원합니다. 조합을 실제 착용 기록에 적용한 뒤 피드백을 저장합니다.

### 날짜별 기록과 동기화

닉네임은 앞뒤 공백·유니코드 표기·영문 대소문자를 정규화합니다. 닉네임 방식은 인증이 아니며, 닉네임을 아는 사람은 같은 프로필을 조회·수정할 수 있습니다.

사용자별 하루 한 기록을 유지합니다. 서버는 저장 ID를 `day:YYYY-MM-DD`로 정규화하여 같은 날짜 재저장을 수정으로 처리합니다. 과거 기록을 수정할 때는 당시 날씨와 시각을 유지합니다.

삭제한 기록은 목록과 개인화 계산에서 제외합니다. 구형 중복이나 백업으로 되살아나지 않도록 날짜별 최소 삭제 표시를 남기며, 사용자가 같은 날짜를 명시적으로 다시 기록하는 것은 가능합니다.

배포 DB를 사용하는 기기는 재접속·새로고침 시 최신 기록을 가져옵니다. 다른 기기에서 수정한 화면을 실시간으로 자동 갱신하는 기능은 아직 없습니다. 브라우저에는 마지막 닉네임만 기억합니다.

## 예상 보온 범위의 기준

한 점의 목표 대신 **예상 보온 범위**를 안내합니다. 옷별 점수는 고정하고, 실제로 편했던 기록을 기준으로 개인의 범위를 조정합니다.

- 기록 한두 개로도 대략적인 기준을 잡도록, 기록마다 기본 기준보다 몇 점 더(덜) 입는 사람인지 계산해 15℃ 이내의 다른 기온에도 옮겨 씁니다(‘기록으로 추정’). 설정은 기록 1개만큼의 비중이라 기록 1개면 절반, 2개면 약 2/3가 기록 쪽으로 이동합니다.
- 추위·더위 민감도 설정은 한 단계 1점, 최대 ±2점으로 크게 반영합니다.
- 같은 기온대의 세밀한 범위는 체감온도 ±5℃ 안의 실외 기록을 기온 차이만큼 보정해 참고하고, 온도가 가깝고 활동량·야외 시간이 같으면 비중을 높입니다.
- ‘적당했어요’는 기준점으로 사용합니다. 기록이 적으면 임시 기준을 함께 참고하고, 충분한 유사 기록이 있으면 실제 착용 점수가 우선합니다.
- ‘추웠어요/더웠어요’는 더 따뜻하거나 가벼운 방향의 근거로 사용하며, 한 단계마다 몇 점이라고 환산하지 않습니다.
- 기록이 없으면 임시 기준, 적으면 학습 중, 편안했던 근거가 쌓이면 개인 기록 기준으로 표시합니다. 서로 모순되는 응답은 ‘기록이 엇갈려요’로 안내합니다.
- 외출 중 체감이 바뀌었거나, 옷을 벗거나 더 입었거나, 하의·소품이 보통과 다른 기록은 점수를 바꾸지 않고 비중만 낮춥니다.
- 기록할 때 그날 보여준 추천을 함께 저장해, 이후 착용감과 비교한 적중 현황을 보여줍니다.
- 사용한 날짜·착용 조합·체감을 화면에 표시합니다. 적당했던 조합은 다시 불러올 수 있고 자동 추천에서도 후보로 참고합니다.
- 삭제·실내·기온 차이가 큰 기록은 제외하며, 같은 날짜를 여러 번 수정해도 학습 근거가 중복되지 않습니다.

기록이 없을 때의 임시 중심은 기존 식인 `1 + (26 - 체감온도) × 0.3`과 초기 민감도·활동·야외 시간을 사용합니다. 이 식은 검증 중인 앱 가정이며 개인 기록이 쌓인 뒤에도 정답으로 고정하지 않습니다. 예를 들어 같은 조건에서 보온 6점이 반복해서 적당했다면 초기 식보다 그 기록 주변의 범위를 우선합니다.

**범위는 통계적 신뢰구간이나 제품의 실측 보온 성능이 아닙니다.** 기온 차이 허용 폭·기록 가중치·범위 폭도 초기 설계값입니다. 실제 추천 정확도는 이후의 착용 피드백으로 검증해야 합니다. 신규 DB 스키마 실행은 필요하지 않습니다.

## 로컬 실행

```powershell
git clone https://github.com/rheejeongseok/weather-quest.git
cd weather-quest
npm start
```

기본 주소는 http://localhost:3002 입니다. 같은 Wi-Fi의 다른 기기는 `http://PC의내부IP:3002`로 접속합니다. 서버가 실행 중이어야 하며 Windows 방화벽에서 해당 포트 접근이 허용되어야 합니다.

Supabase 환경변수가 없으면 `data/weather.sqlite`를 생성합니다. 로컬 SQLite 데이터는 배포 서버와 공유하지 않습니다. `PORT`, `HOST`, `DATA_DIR`로 포트·바인딩 주소·로컬 DB 폴더를 바꿀 수 있습니다.

### 로컬에서도 Supabase 사용하기

`.env.example`을 `.env.local`로 복사한 뒤 같은 프로젝트의 URL과 서버용 키를 넣습니다.

```dotenv
SUPABASE_URL=https://jzzdgoirtokaiwwmmitd.supabase.co
SUPABASE_SECRET_KEY=서버용_Secret_key
```

```powershell
node --env-file=.env.local server.mjs
```

`npm start`는 `.env.local`을 자동으로 읽지 않습니다. 키가 들어간 파일은 Git에서 제외되며 비밀 키를 소스나 브라우저 코드에 넣지 않습니다.

## Supabase · Vercel 배포

현재 사용자가 지정한 서울 프로젝트의 연결 주소는 `https://jzzdgoirtokaiwwmmitd.supabase.co`입니다. 이전 싱가포르 프로젝트의 URL과 키를 혼용하지 않습니다. 아래 설정은 사용자가 대시보드에서 적용해야 하며 저장소의 예제 파일만 바꿔서는 실제 배포 환경변수가 변경되지 않습니다.

1. 서울 프로젝트 SQL Editor에서 [schema.sql](supabase/schema.sql)을 실행합니다.
2. Vercel 환경변수에 `SUPABASE_URL`과 **같은 서울 프로젝트의** `SUPABASE_SECRET_KEY`를 등록합니다. 사용하는 Production·Preview 환경에 적용합니다.
3. GitHub 저장소를 연결하고 Framework Preset은 **Other**, Node.js는 **24.x**, Root Directory는 저장소 루트로 설정합니다.
4. 빌드·출력 설정은 `vercel.json`을 사용합니다. 빌드는 `npm run build`, 출력 폴더는 `dist`이며 API는 `api/handler.mjs`가 처리합니다.
5. 환경변수 변경 후 재배포합니다. 기존 배포에는 변경값이 소급 적용되지 않습니다.

Vercel에서는 Supabase 설정이 빠지면 오류를 반환하며 임시 SQLite로 대체하지 않습니다. 현재 DB 스키마는 `wq_profiles`, `wq_records`, 병합 함수 `wq_import_records`를 사용합니다.

| 오류 | 확인할 항목 |
| --- | --- |
| 환경변수 누락 | 두 변수의 이름·값·적용 환경, 재배포 여부 |
| DNS 조회 실패·서버 연결 실패 | 새 Project URL인지, 오타·이전 주소·프로젝트 실행 상태 |
| 키 인증 실패 401 | URL과 키가 같은 프로젝트인지, 키 활성 상태 |
| 접근 권한 오류 403 | 서버용 키 종류와 테이블 권한 |
| 테이블·함수 없음 404 | 새 프로젝트에서 `schema.sql` 실행 여부 |

`SUPABASE_URL`에는 대시보드 주소 대신 `https://프로젝트ID.supabase.co` 형태의 Project URL을 넣습니다. 비밀 키는 앞뒤 여백을 정리하며 내부 공백·줄바꿈은 오류로 안내합니다.

## 백업과 프로젝트 이전

설정의 JSON 내보내기는 현재 닉네임의 프로필 정보와 기록을 저장합니다. 가져오기는 **현재 프로필에 없는 날짜의 기록만** 추가하며 기존 날짜·설정은 덮어쓰지 않습니다. 적용 전 현재 데이터를 백업 다운로드합니다.

전체 Supabase 이전은 JSON 가져오기와 별개입니다. [export-migration.sql](supabase/export-migration.sql)은 모든 프로필·설정·기록·삭제 표시를 이전할 SQL을 생성하는 읽기 전용 도구입니다. 실제 이전 절차와 확인 사항은 [서울 이전 안내](docs/SEOUL-MIGRATION.md)를 따릅니다. 현재 앱의 두 테이블을 대상으로 하며, 대규모 DB에는 공식 dump/restore 절차를 사용합니다.

### DB 구조

| 테이블 | 내용 |
| --- | --- |
| `wq_profiles` | 공통 계정(id·닉네임). `data` 칸은 예전 저장 방식으로, 새 테이블이 비어 있을 때만 읽어 옮김 |
| `wq_cloth_settings` | 옷차림 설정(프로필당 한 줄) |
| `wq_records` | 옷차림 착용 기록 |
| `wq_subway_saved` | 지하철 즐겨찾기·최근 경로·경로 기준·실시간 노선(프로필당 한 줄) |

서랍 테이블은 모두 `profile_id`로 프로필에 연결되고, 프로필을 지우면 함께 지워집니다. 각 서랍은 `core/profile.mjs`의 `profilePart`로 자기 몫을 프로필 응답에 붙이고, `db.appGet/appSet(테이블, 프로필 id)`으로 자기 테이블만 읽고 씁니다. 기존 DB는 `supabase/migrations/2026-11-23-drawer-tables.sql`을 한 번 실행해 옮깁니다.

### 새 서랍 추가하기
1. `apps/<이름>/routes.mjs`에서 `handle(ctx)`를 내보내고(맞지 않는 요청은 `false` 반환) `core/handler.mjs`의 `apps` 목록에 넣습니다.
2. 화면은 `public/<이름>/`에 두고 `public/shell/main.js`의 `showApp`·홈 서랍 목록·모바일 메뉴(`public/index.html`)에 연결합니다.
3. 스타일은 `public/styles/<이름>.css`를 만들어 `index.html`에 추가합니다.
4. 저장할 데이터가 있으면 `wq_<이름>_...` 테이블을 만들어(`profile_id` 연결) `core/store.mjs`의 `APP_TABLES`에 이름을 넣고, `supabase/schema.sql`과 새 마이그레이션 SQL에도 추가합니다.

실제 보유 옷장, 하의 점수 학습, 실시간 화면 동기화는 아직 포함하지 않았습니다.
